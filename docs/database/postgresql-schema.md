# 1. Purpose

This document defines the detailed logical PostgreSQL schema for the AI-Powered Cafe Management System.

The purpose is to translate the approved domain model, aggregate model, database design, and Entity Relationship Diagram into a database-level specification before implementation using Drizzle ORM.

This document defines:

- Tables
- Columns
- Data types
- Primary keys
- Foreign keys
- Constraints
- Unique rules
- Status values
- Indexes
- Delete behavior
- Timestamp conventions
- Historical-data requirements
- Transactional considerations
- Data consistency rules

This is a logical database specification. It is not yet the final Drizzle ORM implementation.

---

# 2. Database Technology

The initial database technology is:

    PostgreSQL

The application will access PostgreSQL through Drizzle ORM.

The final SQL generated by Drizzle will be validated against this logical specification.

---

# 3. Database Design Principles

The database shall follow these principles:

1. Maintain strong referential integrity.
2. Preserve important historical business records.
3. Use constraints to prevent fundamental invalid states where practical.
4. Keep higher-level business rules primarily in the application/domain layer.
5. Avoid unnecessary duplication of authoritative data.
6. Use transactions for operations that must remain atomic.
7. Design indexes from actual access patterns.
8. Preserve financial and audit history.
9. Keep domain ownership clear.
10. Avoid premature optimization.
11. Support future functionality without unnecessary schema redesign.
12. Prefer explicit relationships over ambiguous data references.
13. Use appropriate numeric precision for financial and quantity data.

---

# 4. Identifier Strategy

The initial schema shall use UUID primary keys.

Example:

    id UUID PRIMARY KEY

UUID generation may be implemented by PostgreSQL or the application, provided the strategy remains consistent.

Join tables may use composite primary keys where appropriate.

Example:

    (user_id, role_id)

---

# 5. Timestamp Strategy

Timestamp columns shall use timezone-aware PostgreSQL timestamps.

Preferred type:

    TIMESTAMPTZ

Common fields:

    created_at
    updated_at

Lifecycle-specific fields may include:

    confirmed_at
    completed_at
    cancelled_at
    received_at
    occurred_at
    sent_at
    read_at

The application and database shall use one consistent timezone strategy.

# 12. Inventory

## 12.1 inventory_items

Represents tracked physical stock.

| Column           | Type          | Constraints                 |
| ---------------- | ------------- | --------------------------- |
| id               | UUID          | PK                          |
| ingredient_id    | UUID          | UNIQUE, FK → ingredients.id |
| department_id    | UUID          | FK → departments.id, NULL   |
| current_quantity | NUMERIC(14,3) | NOT NULL                    |
| unit_of_measure  | VARCHAR       | NOT NULL                    |
| reorder_level    | NUMERIC(14,3) | NOT NULL                    |
| status           | VARCHAR       | NOT NULL                    |
| created_at       | TIMESTAMPTZ   | NOT NULL                    |
| updated_at       | TIMESTAMPTZ   | NOT NULL                    |

Constraints:

    current_quantity >= 0
    reorder_level >= 0

### Inventory consistency rule

`stock_movements` is the authoritative inventory ledger.

`current_quantity` is a maintained current-state value for efficient reads and must remain transactionally consistent with valid stock movements.

The application shall not update `current_quantity` independently of the corresponding stock movement.

---

## 12.2 stock_movements

Represents a change to inventory quantity.

| Column            | Type          | Constraints             |
| ----------------- | ------------- | ----------------------- |
| id                | UUID          | PK                      |
| inventory_item_id | UUID          | FK → inventory_items.id |
| movement_type     | VARCHAR       | NOT NULL                |
| quantity          | NUMERIC(14,3) | NOT NULL                |
| unit_cost         | NUMERIC(12,2) | NULL                    |
| reference_type    | VARCHAR       | NULL                    |
| reference_id      | UUID          | NULL                    |
| occurred_at       | TIMESTAMPTZ   | NOT NULL                |
| created_by        | UUID          | FK → users.id           |
| created_at        | TIMESTAMPTZ   | NOT NULL                |

Suggested movement types:

    PURCHASE
    CONSUMPTION
    WASTE
    ADJUSTMENT_IN
    ADJUSTMENT_OUT
    TRANSFER

Constraint:

    quantity > 0

### Reference rule

`reference_type` and `reference_id` provide a flexible link to the business operation that caused the movement.

Because this is a polymorphic reference, PostgreSQL cannot enforce the target foreign key directly.

The application must therefore validate that the referenced business record exists and is compatible with the declared `reference_type`.

# 21. Financial Data Rules

Financial data shall be modeled using:

    NUMERIC(12,2)

or another explicitly selected fixed-precision numeric type.

Floating-point types shall not be used for monetary values.

The following are financial records:

    Menu prices
    Order prices
    Order totals
    Payments
    Refunds
    Credit balances
    Credit transactions
    Purchase costs
    Waste costs
    Delivery fees
    Asset purchase costs

Historical financial records must remain stable after later configuration changes.

For example:

    Current Cappuccino price = 100 ETB

    Historical Order Item price = 80 ETB

Changing the current menu price must not modify the historical order.

---

# 22. Inventory Consistency Rules

The inventory ledger consists of stock movements.

Conceptually:

    Opening Stock
    + Purchases
    + Adjustments In
    + Transfers In
    - Consumption
    - Waste
    - Adjustments Out
    - Transfers Out
    =
    Closing Stock

The implementation shall ensure that changes to the current inventory state and corresponding movements occur atomically.

Inventory should not be silently changed without an auditable movement.

---

# 23. Customer Credit Consistency Rules

Customer credit should be treated as a financial ledger.

Conceptually:

    Opening Balance
    + Charges
    + Authorized Adjustments
    - Payments
    =
    Current Balance

The implementation shall update the credit transaction history and maintained balance within an appropriate transaction boundary.

The balance must remain reconcilable from the transaction history.

---

# 24. Order Payment Consistency

An order's financial payment state should be derived from payment transactions.

Conceptually:

    Successful Payments
    -
    Eligible Refunds
    =
    Net Paid Amount

Then:

    Net Paid Amount = 0
        → UNPAID

    0 < Net Paid Amount < Order Total
        → PARTIALLY_PAID

    Net Paid Amount >= Order Total
        → PAID

These payment summary states belong to the order/application layer and are not required to be stored as an individual payment status.

---

# 25. Delete and Cascade Policy

The following records should generally not be physically deleted as a normal business operation:

    Orders
    Payments
    Refunds
    Credit Transactions
    Stock Movements
    Waste Records
    Audit Events

Historical records should be preserved.

For configuration entities, possible lifecycle approaches include:

    Deactivate
    Archive
    Soft Delete

Cascade deletion must be used cautiously where a parent has historical or financial children.

The final foreign-key deletion actions shall be explicitly defined in the Drizzle implementation.

# 27. Transaction Boundaries

The application should use database transactions for operations that must remain atomic.

## 27.1 Order Creation

Potential transaction:

    Create Order
    +
    Create Order Items
    +
    Record applicable credit transaction or required payment state

## 27.2 Inventory Receipt

Potential transaction:

    Create Purchase
    +
    Create Purchase Items
    +
    Create Stock Movements
    +
    Update Current Inventory State

## 27.3 Credit Payment

Potential transaction:

    Record Payment
    +
    Record Credit Transaction
    +
    Update Credit Balance

## 27.4 Payment Confirmation

A payment-provider confirmation workflow must update the relevant payment state and any dependent business state atomically where required.
